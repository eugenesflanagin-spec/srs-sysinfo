# SRS 2.4.0 - Memory Timings, a much harder GPU Burnin, stop limits up to 110 C

An update to SRS 2.3. Everything from 2.3 is still there, and settings, tabs and lineups carry over.

## What's new

- **Memory Timings: the live DDR5 timings.** On AMD Ryzen 7000 / 9000 desktop processors the
  Memory page's **Memory Timings** tab now shows what the memory really runs at: every timing of
  each channel (CL, tRCD, tRP, tRAS, tRC, the refresh timings and about 30 more, each with a short
  meaning and the time in nanoseconds), the memory, controller and fabric clocks (MEMCLK, UCLK,
  FCLK and their ratio), the SoC voltages, and the controller settings (Gear Down Mode, command
  rate, power down ...). It needs the `ryzen_smu` driver (AUR `ryzen_smu-dkms-git`) and one
  **Run as root**; everything is only read. For every DDR5 module, without root: maker, part
  number, size, DRAM maker, date, temperature and its JEDEC, EXPO and XMP profiles - so you can
  see the profile next to what the BIOS set.
  - **BIOS memory settings** (ProcODT, drive strengths, RTT values, the DIMM voltages the BIOS set)
    come from the BIOS's AMD AOD table when the kernel allows reading it (see below).
  - **DIMM voltages from the modules' own power chips (PMIC)** are an opt-in under **Options**,
    off by default, and ask first.
  - **Intel** Core 6th gen to Core Ultra: live speed and CL-RCD-RP-RAS, **experimental**.
- **GPU Burnin loads the graphics card much harder.** A faster matrix multiply on all four back
  ends (Vulkan, ROCm / HIP, CUDA / ZLUDA, OpenCL). On my Radeon RX 9070 XT, FP32, 0 errors on every
  back end: CUDA via ZLUDA 5.3 -> 17.2 TFLOPS, Vulkan 6.2 -> 16.2, OpenCL 3.4 -> 13.4 and
  ROCm / HIP 3.4 -> 13.0. The card draws more power and gets hotter, as a burn-in should. The GPU Compute
  comparison keeps the old kernel, so its numbers stay comparable. The live readout no longer
  shows 0.0 multiplications per second.
- **Stop limits up to 110 C.** The CPU and GPU stop limits of Stress & Burnin now go up to 110 C.
  Over 100 C, SRS asks once whether you accept the risk (No puts both back to 100). The CPU limit
  is remembered, and the folded **GPU options** line now shows the GPU's own limit, so it is never
  hidden. Command line: `--accept-high-limit` for `burn` and `gpu-burn`.
- **Pages that said "not read" now show their data:** System CMOS (no root needed any more),
  System EBDA, the GPU's VBIOS image (from the driver's own copy: signature, checksum, images, part
  number), the GPIO pin states, the factory core ranking on AMD Fuses (no root needed), package and
  per-core power from the RAPL counters on MSR Setup (with a plain-English legend on MSRs), and the
  UEFI System Table and firmware-update (ESRT) details on Firmware.
- **Update hardware lists** (Tools page, or `sysreport-search update-lists`): fetches the newest
  PCI, USB and monitor maker name lists from their official sources, only when you ask, into your
  own folder. SRS then uses whichever copy is newer, yours or the system's.
- **ACPI method evaluation, for experts** (Tools page): run one ACPI method of your BIOS as root
  through the `acpi_call` module and see its result. Off until you accept a warning once; every
  call is logged.
- **Read the embedded controller** (Options, off by default, asks first): a read-only copy of the
  EC's 256 registers on the ACPI Embedded Controller page.
- Fixes: the Power & Cost estimates note no longer opens taller than the screen; the OpenCL page
  works with both kinds of `clinfo`; Redact Reports also masks hexdump lines in copied text; the
  CPU flags are wrapped and the GPIO table lines up.

Full list in [CHANGELOG.md](CHANGELOG.md).

## Tested on one PC (and what that means)

I build and test SRS on a single machine: a Ryzen 7 7800X3D with a Radeon RX 9070 XT, on a wired
connection. I've done everything I can for the rest (checks that don't need the hardware, careful
reading of the docs, test builds), but I can't try what I don't own. So anything that needs other
hardware, such as NVIDIA CUDA, Intel graphics, ROCm/HIP or OpenCL setups other than mine, Wi-Fi or
VPN network tests, or ARM and 32-bit builds, may have a bug or two I haven't met yet. If you find
one, please tell me: open an issue on
[GitHub](https://github.com/eugenesflanagin-spec/srs-sysinfo/issues) with your hardware and the
report SRS made, and I'll fix it.

What this means for 2.4 in particular:

- **Intel memory timings are EXPERIMENTAL and untested on real Intel hardware.** I have no Intel
  PC; the decoding was checked with made-up register values only. If you have an Intel Core
  6th gen to Core Ultra PC, please compare the Memory Timings page with your BIOS and report what
  you see, right or wrong.
- **AMD memory timings** were checked on one Ryzen 7 7800X3D with DDR5-6000 EXPO. The Ryzen 9000
  PM table layout (which gives the clocks and SoC voltages) is not checked, so some of those rows
  may be missing or wrong there. Other AMD processors say "not supported yet".
- **The BIOS memory settings (AOD table)** sit in memory that most Linux kernels keep from programs
  (kernels built with IO_STRICT_DEVMEM). Reading them needs the kernel option `iomem=relaxed`,
  which weakens that protection. **SRS never asks you to change it**; without it the page says why
  that part is missing, and everything else works. The table's layout was checked on one BIOS and
  is only shown when its timings match the live ones.
- **ACPI method evaluation can change hardware state.** A method can switch devices on or off,
  change fan, power or performance settings, write BIOS settings, or hang or reboot the PC. It is
  for experts who know which method they run; the authors are not responsible for any damage.
- The PMIC and embedded controller opt-ins were not checked on real hardware yet, and the EBDA dump
  was not either (my UEFI PC has none).
- GPU Burnin's new kernel ran on my real card with all four back ends (AMD only: NVIDIA's own CUDA
  driver was not tried). A stronger load also finds a shaky overclock sooner: during testing my
  own memory-fabric overclock (FCLK) reset the PC under this load and had to go back down.

## Upgrading from 2.3.x

Install the new package over the old one; nothing has to be set up again. Run **Menu -> Run as
root** once to collect the new root data (memory timings, VBIOS image, GPIO pins, RAPL power,
EBDA, UEFI tables). For the AMD live timings install the `ryzen_smu` driver first; for ACPI method
evaluation the `acpi_call` module.
