# SRS 2.6.0 - GPU Tuning (read-only), GPU Burnin for programs and a fairer GPU Compute comparison

An update to SRS 2.5. Everything from 2.5 is still there, and your settings, tabs and lineups carry
over.

## What's new

- **GPU Tuning, a new tab on Benchmarks & Stress** (right after Stress & Burnin; Menu -> Benchmarks &
  Stress -> GPU Tuning (Read-Only)...; `sysreport-search gpu-tune status`).
  - It shows what each graphics card is **set to right now**: the voltage offset (undervolt), the core
    clock offset (overclock), the highest memory clock and the power limit, with the ranges the
    driver accepts and the live temperature, power and clock.
  - It also shows whether **Tux Burner** is installed and its service is running (Tux Burner is a
    separate free program that changes GPU settings and holds the safety limits), the voltage floor
    its service reports, and whether **LACT** is running, with LACT's saved values for the card and
    whether the card is at them.
  - **This version only shows.** No button on the tab changes anything, and SRS never writes to a
    graphics card. Changing settings (and searching for a safe undervolt) comes in a later version,
    through Tux Burner.
  - AMD RDNA 4 (RX 9000) and RDNA 3 (RX 7000) cards are read straight from the kernel's files, with no
    other program. NVIDIA cards show their values through Tux Burner's service. Older AMD cards and
    Intel cards get a "not supported yet" note. A card that is asleep is not woken.
  - Without Tux Burner the tab still works and says in two sentences what Tux Burner adds and how to
    install it.
- **GPU Burnin for other programs.** `sysreport-search gpu-burn --yes --json` prints the result as one
  JSON object and ends with an exit code a program can act on (0 PASS, 10 stopped, 11 wrong results,
  12 could not start, 13 ended early, 14 a GPU reset, 15 the temperature limit). `--json-live` adds a
  line every half second, `--pci ADDR` picks the card by its PCI address. Without `--json` nothing
  changes.
  - **`--watch-kernel`** reads the kernel log during the run and for 5 seconds after it. A GPU pushed
    too far often does not fail inside the test: the driver resets it, and the program that crashes is
    the desktop. With the watch on, such a reset fails the run even when the test's own numbers were
    right. If the kernel log cannot be read, SRS says so instead of reporting "nothing seen".
- **GPU Compute comparison**
  - It now runs in its own process: a GPU runtime that crashes (as ROCm 10.1's HIP did as soon as
    ZLUDA's CUDA started) no longer closes SRS. The back end that crashed is left out and the
    comparison runs again without it.
  - ROCm / HIP, CUDA and OpenCL lose less speed to SRS's own code. AMD's compiler is asked for
    64-wide waves like the Vulkan driver uses, the launch test no longer sleeps while it waits, and on
    Mesa's Rusticl the run is timed on the host and copies go through the GPU. The work and every
    result check are the same. A new **how it ran** line under the table says what applied.
  - Measured on my Radeon RX 9070 XT (10 s per test, the build before these changes and this one, one
    after the other in the same session; Vulkan = 100%):

    | Test | Back end | Before | After |
    |---|---|---|---|
    | FP32 multiply-add chain | ROCm / HIP | 19715 GFLOPS (38%) | 40680 (78%) |
    | FP32 multiply-add chain | OpenCL (ROCm) | 19918 GFLOPS (38%) | 39156 (75%) |
    | Kernel launch round trip | ROCm / HIP | 105 µs | 17.1 µs |
    | Kernel launch round trip | CUDA (ZLUDA) | 105 µs | 17.4 µs |
    | Kernel launch round trip | OpenCL (ROCm) | 106 µs | 21.0 µs |
    | Kernel launch round trip | OpenCL (Rusticl) | 310 µs | 40.4 µs |
    | Upload | OpenCL (Rusticl) | 25.9 GB/s | 53.0 GB/s |
    | Download | OpenCL (Rusticl) | 5.25 GB/s | 52.6 GB/s |
    | FP32 matrix multiply, own kernel | OpenCL (Rusticl) | 58% | 69% |

    What did **not** move on this card: the own-kernel FP32 matrix multiply on ROCm / HIP (57% -> 61%)
    and OpenCL (ROCm) (59% -> 58%), and the multiply-add chain on CUDA through ZLUDA (38% -> 40%) and on
    Rusticl (68% -> 65%). OpenCL (ROCm)'s FP64 rows came out about 7% lower in the second run, which I
    cannot explain yet. It is one run each, and my desktop shell was crashing (not SRS's doing) during
    the last minute of the second run, which can only have lowered its numbers. Other GPUs were not
    measured. The full table is in EVIDENCE.md.
  - GPU Burnin is not changed at all.
- **CPU telemetry from the SMU PM table** (Ryzen 7000 desktop, through ryzen_smu, read-only): VCORE,
  VID, package power and its limit, the hotspot, and one voltage, temperature and effective clock per
  core.
- **Memory Timings**: five more DDR5 timings (tMODPDA, tMRDPDA, tTRCPAGE, tWRPRE, tRDPRE), the
  **AGESA version** of the BIOS, and the AOD table through QTuxTimings' `aod_voltages` module when
  the kernel keeps it out of `/dev/mem`.
- **CPU speeds at the real base clock.** On a PC with a raised BCLK or eCLK (for example 104 MHz),
  Base Speed, Maximum Speed and the CPU Speeds table were too low, because the kernel works them out
  at 100 MHz. They are now shown at the measured base clock.
- **The Big Top from the tray.** The tray menus have **The Big Top (Task Manager)**, and closing the
  main window to the tray leaves The Big Top open. The tray meters have their own **Tray Meter
  Speed** and are lighter on the desktop's tray.

- **`srs-root` is safer.** Run without root, with `--help` or with a mistyped option it used to
  collect anyway and could replace good cached data with error texts; now it checks first and says
  "needs root ... Nothing was changed." It also no longer writes inside your home folder as root: the
  data is collected in a root-only folder and handed over at the end by a process running as you, which
  closes a symlink issue and means an interrupted run keeps the data you had. `sudo srs-root` now
  collects for you, not for root.

Full list in [CHANGELOG.md](https://github.com/eugenesflanagin-spec/srs-sysinfo/blob/main/CHANGELOG.md).

## Tested on one PC (and what that means)

Tested on one PC (Ryzen 7 7800X3D, RX 9070 XT, ASUS X870, KDE Plasma 6 Wayland). I've done
everything I can for the rest: tests on made-up data, fake devices and stand-in services, careful
reading of the docs, and test builds. But I can't try what I don't own. These parts were
**not tried on real hardware** and may have a bug or two I haven't met yet:

- **GPU Tuning** with a real Tux Burner service (made-up system files and a stand-in for Tux Burner's
  service were used; on the real card its status was read and matched what LACT shows)
- `gpu-burn --watch-kernel` with a real GPU reset (the kernel messages were written from the drivers'
  wording; one run on the real card passed, with nothing to see in the log)
- NVIDIA graphics cards and CUDA on real NVIDIA hardware (only a stand-in for NVIDIA's library), and
  Intel GPUs
- RDNA 3 (RX 7000) and older AMD cards, APUs (processors with built-in graphics)
- laptops and PCs with two graphics cards (hybrid graphics)
- the new GPU Compute comparison numbers on any GPU other than my RX 9070 XT (measured there once
  before and once after, see above)
- the new `srs-root` through pkexec and the boot unit: the tests run its checks and its hand-over
  step as a normal user; as root it was run once through sudo on my PC (exit 0, the cache folder
  mine with mode 700, every file there), before one last small change to it that was tested as a
  normal user only
- the PM table telemetry on 16-core Ryzen 7000 and on other processors (they say "not known")
- ARM (aarch64) and 32-bit builds from source (they compile, but were not tried on an ARM machine)
- real installs on other distributions (each package is install-tested in a clean container)

If you find a bug, please tell me: open an issue on
[GitHub](https://github.com/eugenesflanagin-spec/srs-sysinfo/issues) with your hardware and the
report SRS made, and I'll fix it.

## Upgrading from 2.5.x

Install the new package over the old one; nothing has to be set up again. GPU Tuning needs nothing
else for reading; for Tux Burner's part, install Tux Burner and its service (the tab gives the
command).
