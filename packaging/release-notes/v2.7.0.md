# SRS 2.7.0 - Text size, and s-tui's stress loads in Stress & Burnin

An update to SRS 2.6. Everything from 2.6 is still there, and your settings, tabs and lineups carry
over.

## What's new

- **Text size for all of SRS.** Make every window's text larger or smaller, from 50 % to 300 %: the
  reports, buttons, menus and headings, in the main window and the classic view.
  - **Ctrl + Plus** (or Ctrl + =, or + on the number pad) larger, **Ctrl + Minus** smaller,
    **Ctrl + 0** back to 100 %.
  - **Ctrl + mouse wheel**: wheel forward (away from you) larger, back smaller. The page under the
    mouse does not scroll meanwhile.
  - Or **Menu -> Options -> Text size**. It is remembered.
  - The reports' columns grow with the text, so tables stay lined up. Only SRS changes; the desktop
    and other programs keep their size. Icons keep their size, and windows do not grow by
    themselves.
- **More loads in Stress & Burnin**, after the stress options of s-tui (SRS's own code; no code
  copied).
  - A **CPU load** chooser next to Same CPU / Swap CPU. Besides **Whetstone** (as before, still the
    default) the CPU workers can run:
    - **Matrix multiply** - double-precision matrix multiplications with the widest vector units
      the CPU has (AVX-512 or AVX2, with multiply-add (FMA), or SSE2). It is the hottest load and the one to test a
      Curve Optimizer / undervolt or an overclock with. Every answer is checked; a wrong one fails
      the run and names the CPU it came from.
    - **SHA-256** - hashing with the CPU's SHA instructions when it has them; every digest checked.
    - **Square root** - square roots of whole-number squares, every result checked (the classic
      `stress -c` load).
  - A folded **Memory, sync and disk loads** line, for loads that run beside the CPU and GPU
    loads, or on their own:
    - **Memory workers x MB** - each writes its own block of memory and reads it all back; a wrong
      value fails the run. All together they may use at most 75 % of the free memory; SRS refuses
      to start above that.
    - **Sync workers** - each rewrites 64 KB of a file and flushes it to the disk, over and over.
    - **Disk write workers x MB** - each writes a file of that size over and over, with data that
      cannot be compressed, flushed every 16 MB. The free space is checked first. **An SSD wears
      with every write**: a fast NVMe drive can take 1-2 TB in 15 minutes, so run it briefly, or on
      a drive you do not mind wearing. The start question says so too.
    - **in folder** - the drive to test (default `~/.cache/srs`). The files have no name in the
      folder and are gone when the run ends, even if SRS is killed.
  - They follow the burn / cool phases (Timed works for them alone too). Stop or the temperature
    limit ends the CPU load at once (measured: under 0.1 s); a disk or sync worker first finishes
    the write or flush it is in, longer on a slow drive.
  - Command line: `sysreport-search burn --load matmul|sha256|sqrt|whetstone`, `--memory N
    --memory-mb MB`, `--sync N`, `--disk N --disk-mb MB --disk-dir DIR`, and `--cpus none` for
    the side loads alone.
- **GPU Burnin after an update.** When SRS was updated (or rebuilt) while it was running, GPU
  Burnin and the GPU Compute comparison failed at once with "exit code 127". They now say: close SRS
  and start it again.

Full list in [CHANGELOG.md](https://github.com/eugenesflanagin-spec/srs-sysinfo/blob/main/CHANGELOG.md).

## Tested on one PC (and what that means)

Tested on one PC (Ryzen 7 7800X3D, RX 9070 XT, ASUS X870, KDE Plasma 6 Wayland). I've done
everything I can for the rest: tests on a hidden test screen, careful reading of the docs, and test
builds. But I can't try what I don't own. These parts were **not tried on real hardware**, or only
briefly, and may have a bug or two I haven't met yet:

- **The new CPU loads** ran briefly (a few seconds, two threads) on my CPU, which has AVX-512 and
  SHA instructions. CPUs with only AVX2, only SSE2, or without SHA instructions use other code
  paths that were not run on real hardware. No long all-core run was done before the release.
- **A wrong result** from a checked load on real faulty hardware: none was at hand. A test build
  that forced one wrong value into each load (Matrix multiply, SHA-256, Square root, memory) failed
  the run every time, as it should.
- **The disk and sync loads** on file systems other than btrfs, and on drives other than my NVMe
  drives (the folder's free space is checked first, and a file system without unnamed temporary
  files falls back to a file that is deleted at once - that fallback was not run).
- **Text size** with desktops other than KDE Plasma 6 Wayland (it uses GTK's own font setting for
  SRS's windows only; the keys and Ctrl + wheel were also tried on X11 on a hidden test screen), and
  very large sizes in small windows. A question box that is open does not take the keys.
- **The disk load's fallback** for file systems without unnamed temporary files, and the 32-bit
  (i686) and ARM (aarch64) command-line builds: built and checked by the compiler only.
- Laptops, Intel CPUs, and ARM.

If you find a bug, please tell me: open an issue on
[GitHub](https://github.com/eugenesflanagin-spec/srs-sysinfo/issues) with your hardware and the
report SRS made, and I'll fix it.

## Upgrading from 2.6.x

Install the new package over the old one; nothing has to be set up again. If SRS is running while
you update, close it and start it again before using GPU Burnin.
